# task-batch-solver

Пакетное выполнение задач: проход по всем файлам в `tasks/*.md` (не рекурсивно, `tasks/done` не трогать) и реализация каждой по-очереди через субагента, работающего как task-solver. Субагент запускается синхронно — следующая задача не начинается, пока не завершена предыдущая (включая коммит).

## Когда использовать

- Пользователь просит: «выполни все задачи», «реализуй задачи из tasks», «прогони бэклог»
- Опционально пользователь может указать порядок или подмножество файлов — тогда идти только по ним

## Процесс

### 1. Собери список задач

- `ls tasks/*.md` — все .md-файлы в корне `tasks/` (в `tasks/` лежат: `admin-panel.md`, `change-password.md`, но список берётся фактический на момент запуска).
- Если файлов нет — сообщить пользователю и завершить.
- Порядок: по умолчанию алфавитный; если пользователь указал порядок — его. Перечисли пользователю, какие задачи и в каком порядке будешь выполнять.

### 2. Для каждой задачи по-очереди

Для каждого файла из списка выполни шаги ниже. **Строго синхронно:** не переходить к следующей задаче, пока не завершены все шаги текущей. Если задача не смогла быть выполнена (ошибка субагента, несоответствие ТЗ, красные тесты после исправлений) — **остановить весь батч**, сообщить пользователю, что случилось и на какой задаче остановились. Не продолжать батч с непролитым коммитом по текущей задаче.

#### 2.1. Запусти субагента

Запусти синхронного субагента из текущей модели вспомогательным скриптом скилла:

```bash
node .pi/skills/task-batch-solver/scripts/run-task.mjs tasks/<name>.md
```

Скрипт создаёт сессию pi через SDK (cwd = корень проекта, сессия in-memory), передаёт субагенту весь контекст:
- системный промпт с контекстом проекта vcode (архитектура, правила, тесты — на основе AGENTS.md),
- полное ТЗ задачи (содержимое файла).

Субагент сам изучает затронутые файлы, реализует задачу, проверяет критерии приёмки (npm run dev, chrome-devtools, curl), пишет тесты и гоняет весь набор (`npm test`). Работает синхронно: скрипт ждёт полного завершения.

- Вывод скрипта — поток работы субагента и итоговый отчёт. Прочитай его полностью.
- Если скрипт завершился с ошибкой (код ≠ 0) — задача не выполнена: остановить батч и сообщить пользователю (что за ошибка, на какой задаче).

#### 2.2. Проверь результат

Прочитай отчёт субагента и убедись:
- Все пункты плана из ТЗ выполнены, критерии приёмки пройдены.
- Тесты написаны и весь `npm test` зелёный. При сомнениях — перепроверь сам: прогони `npm test` ещё раз, при необходимости открой приложение через chrome-devtools и проверь функционал.
- Если проверка не прошла — вернуть субагента на доработку (запустить `run-task.mjs` ещё раз — субагент увидит текущее состояние файлов и продолжит) или исправить самому. Не переходить к следующему шагу, пока всё не зелёное. Если исправить не удаётся — остановить батч и сообщить пользователю.

#### 2.3. Сделай коммит (без пуша)

Только после того, как все проверки и тесты пройдены:

```bash
git add apps tests docs package.json Dockerfile docker-compose.yml
git add -f .pi/skills/task-batch-solver   # скилл коммитится принудительно (.pi в .gitignore)
git commit -m "feat: <краткое описание задачи>"
```

- Сообщение коммита — по конвенции репозитория (`feat:`, `fix:` и т.п.), кратко отражает суть задачи.
- **Без пуша** — деплой и git push не входят в этот скилл.
- Если рабочее дерево чистое (изменений нет) — зафиксировать это и всё равно перенести файл задачи в tasks/done отдельным коммитом либо включить перенос в основной коммит (предпочтительно: перенести файл задачи **до** коммита, чтобы коммит включал и его).

Порядок внутри шага (предпочтительный): перенести файл задачи в `tasks/done` → затем один коммит, включающий и код, и перенос файла, и скилл.

#### 2.4. Перенеси файл задачи в tasks/done

- `tasks/<name>.md` → `tasks/done/<name>.md` (создать `tasks/done`, если её нет).
- Если субагент дополнял ТЗ в ходе работы — файл уже обновлён им; проверить перед переносом.
- Сообщить пользователю: задача закрыта, коммит сделан.

### 3. Итоговый отчёт пользователю

После всего батча — сводка простым языком:

- Сколько задач выполнено, список с кратким описанием каждой (что изменилось в приложении).
- Для каждой задачи: результат тестов и проверок.
- Коммиты, сделанные по задачам (хэши + сообщения), пуш не выполнен.
- Если батч остановился на какой-то задаче — явно указать: какая задача, почему, что сделано до остановки, что осталось.
- Напомнить: для попадания изменений на сервер нужно запустить `./deploy.sh` (по указанию пользователя), а для отправки коммитов — `git push`.

## Важные правила

- Синхронность: одна задача = один полный цикл (субагент → проверка → коммит → tasks/done). Никакой параллельности.
- Субагент работает в in-memory сессии — контекст между задачами не переносится; каждая задача получает свежего субагента с полным контекстом.
- Остановка батча при любой неразрешимой проблеме — не скрывать ошибки и не продолжать молча.
- Локально docker не запускать — только нативный node (`npm run dev`).
- Коммит делается после проверок, а не до; пуш никогда.
