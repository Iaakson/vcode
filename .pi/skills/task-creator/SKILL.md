# task-creator

Превращает сырую идею или устное описание в полное ТЗ, по которому задачу можно реализовать без дополнительных вопросов — самим агентом или человеком.

**Аудитория:** конечный пользователь, как правило, мало осведомлён в разработке. Скилл берёт на себя всю техническую сторону: пользователь описывает желаемый результат своими словами, агент сам решает «как» и «где».

## Когда использовать

- Пользователь просит: «составь задачу», «оформи как задачу», «подготовь ТЗ», «напиши спеку»
- Фича сформулирована одной фразой, и её нужно развернуть до реализуемого описания
- Готовится задача для issue tracker, коммита или будущей сессии агента

## Принцип: агент решает сам, пользователь только подтверждает

Технические решения НЕ выносить на пользователя — принимать самому на основе кодовой базы и здравого смысла:

- **Где и как реализовать** — выбор файлов, эндпоинтов, полей БД, библиотек/подходов. Пользователь не должен выбирать между «PATCH» и «POST» — он не знает, что это.
- **Поведение в граничных случаях** (0 значений, пустые поля, пересечение фич) — выбрать разумное дефолтное поведение и зафиксировать в ТЗ.
- **UI-расположение, стили, формулировки кнопок** — взять в соответствии с существующим дизайном приложения.
- **Формат результата** (число «✓ 3» или «3/5», порядок сортировки, единицы) — выбрать самый понятный для пользователя вариант и упомянуть его в итоговом описании.

Спрашивать пользователя — **только** когда:

1. Желаемый результат реально неоднозначен и ошибка будет стоить переделки (например: «удалить всё» — удаляем выполненные или вообще все задачи?)
2. Решение затрагивает данные пользователя необратимо (удаление, миграция)

Правила вопросов:

- Формулировать **простым языком, без технических терминов** — не «нужен ли PATCH-эндпоинт?», а «можно ли потом менять дедлайн у задачи?»
- Максимум 1–2 вопроса, только по существу. Если вопросов нет — не задавать вовсе.
- Сразу предлагать свой вариант: «Предлагаю X. Подходит?» — пользователю проще подтвердить, чем ответить с нуля.

## Процесс

### 1. Собери контекст (без пользователя)

- Прочитай описание задачи и **сам** определи, что пользователь скорее всего хочет: переформулируй идею в желаемый результат и держи её в голове.
- Изучи кодовую базу: какие файлы затронет фича, как устроены смежные части, есть ли похожий код для переиспользования.
- Для этого проекта (vcode): архитектура и API описаны в корневом `AGENTS.md`. Весь UI — один файл `apps/frontend/index.html`; backend — `apps/backend/server.js` (SQLite через `node:sqlite`, без npm-зависимостей). Изменения API/БД требуют правки и Dockerfile/docker-compose.yml при необходимости.
- Только после этого — 1–2 вопроса простым языком, если решение реально неоднозначно (см. принцип выше). Обычно вопросы не нужны.

### 2. Заполни шаблон

Возьми шаблон из [references/task-template.md](references/task-template.md) и заполни все секции. Правила:

- **Не оставляй пустых секций** — если секция неприменима, напиши «Не требуется» и почему.
- Требования формулируй как проверяемые утверждения («при клике X происходит Y»), а не как пожелания.
- Критерии приёмки — конкретные и воспроизводимые: их можно прогнать вручную в браузере или curl'ом по API.
- Указывай точные пути файлов и точные имена эндпоинтов/полей БД.
- Отмечай edge cases явно — и **сразу фиксируй выбранное поведение**, не оставляй «на усмотрение».
- Секция «Простыми словами» — для пользователя, без технических терминов: что изменится и что он увидит.

### 3. Проверь задачу перед выдачей

Чек-лист готовности:

- [ ] По описанию можно начать реализацию без дополнительных вопросов
- [ ] Все технические решения приняты (нет «на усмотрение исполнителя»)
- [ ] Все затронутые файлы перечислены и существуют (или явно помечены «создать»)
- [ ] Критерии приёмки проверяемы
- [ ] Для vcode: если меняется API или схема БД — упомянуты миграция/совместимость и необходимость `./deploy.sh`
- [ ] Секция «Простыми словами» понятна человеку без опыта разработки
- [ ] Нет противоречий между секциями

### 4. Выдай результат (двумя частями)

- **Для пользователя:** короткий блок «Простыми словами» — что будет сделано и что он увидит, 3–6 предложений без жаргона. Если были вопросы — показать выбранные ответы.
- **Для исполнителя:** полное ТЗ по шаблону одним блоком Markdown (можно сохранить в файл по указанию пользователя, например `tasks/<name>.md`).
- Предложи сразу реализовать задачу — пользователю не нужно отдельно это просить.
