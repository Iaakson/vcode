# Тестирование (vcode)

Тесты на **Jest** (dev-зависимость, `npm install` нужен один раз после клонирования). Два типа тестов:

| Тип | Где | Что проверяет | Скорость |
|-----|-----|---------------|----------|
| **unit** | `tests/unit/` | Целостность проекта, наличие маршрутов/скриптов (без сети и запуска серверов) | секунды |
| **e2e** | `tests/e2e/` | HTTP API против **реальных серверов** — регистрация, вход, задачи, изоляция пользователей | секунды |

## Как запускать

```bash
npm test          # все тесты (unit + e2e) — запускать после каждого функционала
npm run test:unit # только unit
npm run test:e2e  # только e2e
npx jest tests/e2e/auth.e2e.test.js   # один файл
```

При запуске e2e Jest **сам** поднимает backend (порт **3101**) и frontend (порт **3100**) с чистой тестовой БД `apps/backend/data/todos.test.db` (основная `todos.db` не затрагивается), а после прогона останавливает серверы и удаляет тестовую БД. Ничего вручную запускать не нужно. Порты 3100/3101 должны быть свободны.

## Принцип создания тестов

### Что где лежит

```
tests/
├── setup/
│   ├── global-setup.js      # поднимает backend+frontend на 3101/3100 с чистой тестовой БД
│   └── global-teardown.js   # останавливает серверы, удаляет тестовую БД
├── unit/                    # *.test.js — быстрые тесты без сети
└── e2e/
    ├── helpers.js           # api() — fetch с автоматической cookie-сессией; registerUser()
    ├── auth.e2e.test.js     # аутентификация
    └── todos.e2e.test.js    # задачи (создание, done, удаление, clearCompleted, reorder, изоляция)
```

### Правила

1. **Файл — на фичу.** Один e2e-файл на логическую группу (`auth.e2e.test.js`, `todos.e2e.test.js`), внутри — `describe` по фиче и `test` по сценарию. Имя файла обязательно с суффиксом `.test.js` (для e2e — `.e2e.test.js`).
2. **Клиент и сессия.** В e2e используйте хелпер: `const { api, registerUser } = require('./helpers')`. `registerUser('prefix')` создаёт уникального пользователя (имя с timestamp — конфликты между запусками исключены) и возвращает `{ api, username, password, id }`, где `api` уже с cookie-сессией. Cookie хранится автоматически: каждый вызов `api(method, path, body)` возвращает `{ status, data }` и запоминает `Set-Cookie`.
3. **Один клиент на сценарий.** Не создавайте `makeClient()` повторно внутри теста, если нужен тот же пользователь — новый клиент = новая сессия = 401.
4. **Изоляция.** Тесты не зависят от порядка запуска: каждый сценарий сам создаёт свои данные через API (уникальные пользователи). Основная БД не трогается никогда — e2e работает только с `todos.test.db`.
5. **Читаемость.** Названия `describe/test` — по-русски и по смыслу («пометка выполненной (PATCH done) и отмена»), чтобы отчёт падения был понятен без чтения кода.
6. **Не мокать backend.** Смысл e2e здесь — проверять реальные эндпоинты и БД. Моки нужны только если появится внешний сторонний сервис.

### Шаблон нового e2e-теста

```js
// e2e: <фича>
'use strict';

const { api, registerUser } = require('./helpers');

describe('<фича> (e2e)', () => {
    test('<сценарий простыми словами>', async () => {
        const { api: user } = await registerUser('prefix');
        const res = await user('POST', '/api/todos', { text: '...' });
        expect(res.status).toBe(201);
        // ... проверки по сценарию
    });
});
```

### Связь с разработкой функционала

- После реализации каждого функционала запускать `npm test` (все e2e + unit) — всё должно проходить до сдачи/деплоя.
- Новый функционал = новые тесты: сценарии для тестирования прописываются в ТЗ (см. скилл task-creator, секция «Сценарии для тестирования»), тесты пишет task-solver (см. его SKILL.md).
- Для браузерных проверок UI (drag & drop, визуал) по-прежнему используется chrome-devtools вручную — e2e здесь покрывает API-уровень.
