# Админ-панель (управление пользователями)

## Простыми словами
Пользователь `admin` (самый первый в системе, создаётся автоматически) получит кнопку «Перейти в админ панель» вверху страницы. По нажатию откроется отдельная страница `/admin`, где виден список всех зарегистрированных пользователей. Можно открыть карточку любого пользователя и изменить его имя, задать новый пароль или выдать/убрать статус администратора. Обычные пользователи ничего этого не видят: у них нет кнопки, а страница им недоступна.

## Контекст
Сейчас в системе есть только один встроенный пользователь `admin` (пароль из `ADMIN_PASSWORD`), у него нет никаких особых прав, а управление пользователями отсутствует — зарегистрироваться можно, но изменить или просмотреть аккаунты нельзя. Задача добавляет роль «администратор» и страницу управления.

**Принятое решение по статусу администратора:** пользователь `admin` создаётся при старте сервера — это самый первый пользователь, поэтому он автоматически получает статус администратора (миграция ставит ему `is_admin = 1`). Автоматической выдачи роли при регистрации остальных пользователей нет — роль выдаёт только администратор.

## Цель
Администратор видит список всех пользователей на странице `/admin` и может через карточку пользователя менять его имя, пароль и статус администратора; обычные пользователи не имеют доступа к админ-панели.

## Требования
1. Миграция БД (идемпотентная): колонка `users.is_admin INTEGER NOT NULL DEFAULT 0`; при старте `admin` получает `is_admin = 1`.
2. `GET /api/me` возвращает `{id, username, is_admin}` (для неавторизованного — 401, как сейчас).
3. `GET /api/users` (только администратор): список всех пользователей `{id, username, is_admin, created_at, todoCount}` — отсортирован по `id`. Без сессии — 401, под обычным пользователем — 403. Пароли и хэши в ответе не раскрываются.
4. `PATCH /api/users/:id` (только администратор): изменение `{username?, password?, is_admin?}`:
   - `username` — непустая строка, уникальная (иначе 400/409); при смене имени активные сессии этого пользователя остаются действительными.
   - `password` — новая строка минимум 4 символа (иначе 400); сервер генерирует новый `salt` и хэширует через scrypt (как при регистрации).
   - `is_admin` — 0 или 1; **нельзя снять статус администратора с себя, если ты последний администратор** (иначе 400). Свои имя и пароль менять можно.
   - Пользователь не существует — 404.
5. UI: у администратора в шапке появляется кнопка «Перейти в админ панель» (рядом с существующими элементами шапки, в стиле приложения); у обычных пользователей её нет.
6. UI: страница `/admin` открывается по адресу `/admin` (если dev-сервер frontend не отдаёт `index.html` для неизвестных путей — добавить fallback). Без авторизации или под обычным пользователем — редирект на главную.
7. UI: на `/admin` — таблица/список пользователей (имя, статус админа, дата создания, число задач), клик по пользователю открывает карточку с формой: поле «Имя», поля «Новый пароль» (пустое = не менять), переключатель «Администратор», кнопка «Сохранить». После сохранения данные обновляются в списке.
8. Тёмная тема работает и на странице `/admin` (общий стиль приложения).

## API / БД
```
GET    /api/users        — список пользователей (только админ) → 200 | 401 | 403
PATCH  /api/users/:id    — изменить {username?, password?, is_admin?} (только админ) → 200 | 400 | 401 | 403 | 404
```

Схема БД (таблица `users`: id, username UNIQUE, password_hash, salt, created_at):
- добавляется колонка `is_admin INTEGER NOT NULL DEFAULT 0` (идемпотентный `ALTER TABLE` при старте, по образцу миграции `todos.user_id`);
- при старте `admin` получает `is_admin = 1`.

## Edge cases
- Смена имени на уже занятое → 400/409, имя не меняется.
- Пароль короче 4 символов → 400, пароль не меняется.
- Снятие с себя статуса админа, когда других админов нет → 400.
- Снятие статуса админа, когда есть другой админ → разрешено (200).
- PATCH без полей / пустое тело → 200 без изменений (или 400 — на усмотрение реализации, главное — не ломать состояние).
- Обычный пользователь открывает `/admin` в браузере → редирект на главную; запросы к `/api/users` → 403.
- Неавторизованный → 401 (API) / редирект (UI).
- После смены пароля админом у пользователя его старые сессии остаются активными (не выкидываем — из соображения простоты; отмечено явно).

## Критерии приёмки
- [ ] `curl -c c1 -X POST localhost:3001/api/register -d '{"username":"u1","password":"pass1"}'` → 201; `GET /api/me` с c1 → `is_admin: false`
- [ ] Логин под admin (пароль `ADMIN_PASSWORD`), `GET /api/users` → 200, в списке есть `admin` (`is_admin: true`) и `u1`
- [ ] `PATCH /api/users/:id_u1 {"username":"u2","password":"newpass","is_admin":1}` → 200; логин `u2/newpass` работает; `GET /api/me` → `is_admin: true`
- [ ] Под `u2` `GET /api/users` → 200 (теперь он админ); `GET /api/todos` под `u1`-сессией старого имени после смены имени — сессия жива
- [ ] Попытка `u2` снять с себя `is_admin` (если он единственный второй админ... проверить правило «последний админ»: admin снять не может) → `PATCH` на admin `{is_admin:0}` под admin → 400
- [ ] Регистрируем `u3`, под `u3` `GET /api/users` → 403
- [ ] Без сессии `GET /api/users` → 401
- [ ] В UI: под admin видна кнопка «Перейти в админ панель», открывается `/admin` со списком; клик по пользователю → карточка, сохранение имени/пароля/статуса работает; под обычным пользователем кнопки нет, `/admin` → редирект

## Сценарии для тестирования
(e2e — `tests/e2e`, серверы поднимаются сами на 3100/3101 с чистой БД; принципы — `docs/testing.md`)
- статус администратора у admin: логин admin → `GET /api/me` → `is_admin: true`
- список пользователей (позитив): register u1, u2 → админ `GET /api/users` → 200, оба видны, у u1 `is_admin: false`
- негатив: `GET /api/users` без сессии → 401
- негатив: `GET /api/users` под обычным пользователем → 403
- негатив: `GET /api/users/:id` несуществующий → 404
- изменение пользователя: `PATCH {username, password, is_admin:1}` → 200; повторный логин с новым паролем → 200; `is_admin: true` в `/api/me`
- негатив: смена имени на занятое → 400
- негатив: пароль короче 4 символов → 400
- негатив: admin снимает с себя `is_admin` (единственный админ) → 400
- позитив: снятие `is_admin` у второго админа (других ≥ 2) → 200, статус убран
- ответ `GET /api/users` не содержит `password_hash`/`salt`

## План реализации
1. Backend: миграция `users.is_admin` + `is_admin = 1` для admin при старте.
2. Backend: `is_admin` в `getSessionUser`, `/api/me`; хелпер `requireAdmin` (401/403).
3. Backend: `GET /api/users` (с подсчётом задач через `COUNT(todos)`), `PATCH /api/users/:id` с валидацией и правилом «последний админ».
4. Frontend: кнопка в шапке, роутинг `/admin`, список пользователей, карточка с формой, стили (тёмная тема).
5. Frontend server.js: fallback на `index.html`, если нужно.
6. Прогнать тесты: `npm test` (unit + e2e), добавить новые e2e-сценарии из секции выше.

## Деплой
После правок `server.js` и `index.html` — `./deploy.sh` (порт 3000, SQLite в volume — данные и новая колонка мигрируют автоматически при старте). Порты/пути БД не меняются — Dockerfile/docker-compose.yml править не нужно. После деплоя сообщить пользователю пароль admin (из `ADMIN_PASSWORD`, по умолчанию `admin123`).

## Не входит в задачу (out of scope)
- Удаление пользователей (в ТЗ запроса нет — только изменение).
- Просмотр задач пользователя из админ-панели (только счётчик задач в списке).
- Принудительное завершение сессий пользователя при смене пароля.
- Автоматическая выдача роли при регистрации (только admin — первый пользователь — админ автоматически).
