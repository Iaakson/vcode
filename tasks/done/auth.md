# Регистрация и авторизация пользователей (личный список задач)

## Контекст
Сейчас все задачи лежат в общей таблице `todos` без привязки к пользователю — каждый видит и правит один и тот же список (см. AGENTS.md, раздел «Функционал»). Нужна система регистрации/авторизации, чтобы у каждого пользователя был свой список задач, и он мог его вести. Backend — `apps/backend/server.js` на чистом node (без npm-зависимостей, `node:sqlite`, встроенный `node:http`) — это накладывает ограничения на выбор криптографии и сессий.

## Цель
Каждый зарегистрированный пользователь после входа видит и ведёт только свой список задач. Неавторизованный пользователь видит экран входа/регистрации и не имеет доступа к `/api/todos`.

## Требования
1. Регистрация: POST /api/auth/register — создание пользователя {username, password}. Требования к полям: username 3–32 символа, `[a-zA-Z0-9_-]`, уникальный; password минимум 6 символов. Пароль хранится в виде `scrypt`-хеша (salt + hash, встроенный `node:crypto`), НЕ в открытом виде.
2. Вход: POST /api/auth/login — при успешной проверке пароля создаётся сессия (таблица `sessions`: случайный токен `crypto.randomBytes(32)`, expiry 30 дней) и ставится httpOnly cookie `vcode_session`. Ответ содержит `{username}`.
3. Выход: POST /api/auth/logout — удаляет текущую сессию из БД и сбрасывает cookie.
4. Текущий пользователь: GET /api/auth/me — возвращает `{username}` или 401.
5. Все эндпоинты `/api/todos*` требуют валидную сессию: при отсутствии/просрочке — HTTP 401 `{error: 'unauthorized'}` (не редирект — редиректы делает фронтенд).
6. Привязка задач: все CRUD-операции над `todos` фильтруются по `user_id` текущей сессии (SELECT/UPDATE/DELETE с `WHERE user_id = ?`). Пользователь не может прочитать/изменить/удалить чужую задачу (для него она ведёт себя как несуществующая — 404).
7. `POST /api/todos/reorder` меняет порядок только задач текущего пользователя (ids, не принадлежащие пользователю, игнорируются).
8. UI: до авторизации показывается экран входа/регистрации (две вкладки-формы: «Вход» и «Регистрация»); после — обычный список задач. В шапке — имя пользователя и кнопка «Выйти».
9. Состояние авторизации проверяется при загрузке страницы через GET /api/auth/me; при 401 показывается экран входа. Тема по-прежнему хранится в localStorage и не зависит от пользователя.
10. Ошибки входа/регистрации показываются в форме (неверный пароль, занятый username, невалидные поля — 400/401 с текстом ошибки от API).

## API / БД

```
POST   /api/auth/register  — {username, password} → 201 {username}
POST   /api/auth/login     — {username, password} → 200 {username} + Set-Cookie vcode_session
POST   /api/auth/logout    — → 200 {ok} (сбрасывает cookie)
GET    /api/auth/me        — → 200 {username} | 401

GET/POST/PATCH/DELETE /api/todos* — без изменений по формату, но:
  - требуют сессию (401 при отсутствии)
  - действуют только на задачи текущего пользователя
```

Схема БД (существующая таблица `todos`: id, text, done, priority, due, position, created_at):
- Новая таблица `users`: `id INTEGER PRIMARY KEY AUTOINCREMENT, username TEXT UNIQUE NOT NULL, password_hash TEXT NOT NULL, salt TEXT NOT NULL, created_at TEXT NOT NULL DEFAULT (datetime('now'))`
- Новая таблица `sessions`: `token TEXT PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id), expires_at TEXT NOT NULL, created_at TEXT NOT NULL DEFAULT (datetime('now'))`
- Миграция `todos`: `ALTER TABLE todos ADD COLUMN user_id INTEGER REFERENCES users(id)` (через проверку существования колонки в `PRAGMA table_info(todos)` — ALTER не идемпотентен). Существующим строкам присваивается `user_id` выделенного legacy-пользователя `legacy` (создаётся при миграции со случайным паролем), чтобы данные не потерялись, но не были видны обычным пользователям.
- Все запросы к todos добавляют `WHERE user_id = ?` / `AND user_id = ?`; при создании `INSERT` включает `user_id`.

## Edge cases
- Просроченная сессия: любой запрос /api/todos* и /api/auth/me → 401; фронтенд показывает экран входа, данные не теряются.
- Повторная регистрация существующего username → 400 `{error: 'username занят'}`.
- Неверный пароль при входе → 401 `{error: 'неверный username или пароль'}` (без раскрытия, что именно неверно).
- Чужой todo id в PATCH/DELETE/reorder → 404 / игнор в reorder (не 403 — не раскрываем существование).
- Cookie отсутствует / подделан (токена нет в БД) → 401.
- Одновременные сессии одного пользователя разрешены (несколько браузеров) — logout удаляет только текущую сессию (по токену из cookie).
- `DELETE /api/todos` (удалить выполненные) удаляет выполненные только текущего пользователя.
- Устаревшие сессии чистятся лениво: при проверке сессии удаляются протухшие строки этого пользователя (без cron).
- XSS/CSRF: cookie httpOnly + SameSite=Lax; пароли — scrypt с индивидуальным salt.

## Критерии приёмки
- [ ] `curl -c jar -X POST localhost:3001/api/auth/register -d '{"username":"alice","password":"secret1"}'` → 201; повтор → 400
- [ ] `curl -c jar -X POST localhost:3001/api/auth/login -d '{"username":"alice","password":"secret1"}'` → 200 + cookie; неверный пароль → 401
- [ ] `curl -b jar localhost:3001/api/todos` → список alice (изначально пустой); без cookie → 401
- [ ] `curl -b jar -X POST localhost:3001/api/todos -d '{"text":"task A"}'` → 201; `curl -c jar2 .../login` под bob → его список НЕ содержит task A
- [ ] `curl -b jar -X PATCH localhost:3001/api/todos/<id задачи bob>` → 404; DELETE чужого id → 404
- [ ] `curl -b jar localhost:3001/api/auth/me` → `{"username":"alice"}`; после `curl -b jar .../logout` → me и todos → 401
- [ ] В UI: регистрация → сразу список задач; перезагрузка страницы сохраняет вход; «Выйти» возвращает на экран входа; тема не сбрасывается
- [ ] После деплоя существующие боевые задачи доступны в БД (привязаны к `legacy`), ничего не удалено
- [ ] В БД пароли хранятся как хеш (не секрет1): `SELECT password_hash FROM users`

## План реализации
1. Backend: добавить таблицы `users`, `sessions`, миграцию `todos.user_id` + legacy-пользователя в блок инициализации БД.
2. Backend: helpers — парсинг cookie из `req.headers.cookie`, `getUserFromReq(req)` (токен → сессия → пользователь, с ленивой чисткой просроченных), `hashPassword(password, salt)` через `crypto.scryptSync`.
3. Backend: эндпоинты /api/auth/register, /login, /logout, /me (Set-Cookie с `HttpOnly; SameSite=Lax; Max-Age=2592000; Path=/`).
4. Backend: во всех обработчиках /api/todos* — проверка сессии (401), фильтрация и запись по `user_id`.
5. Frontend: состояние `auth` (username | null), экран входа/регистрации (переключатель форм), `onMounted` → GET /api/auth/me.
6. Frontend: обработка 401 в `api()` → сброс auth и показ экрана входа; шапка с именем и «Выйти».
7. Локальная проверка: `npm run dev`, прогнать критерии приёмки curl'ом и в браузере.
8. Деплой: `./deploy.sh`.

## Деплой
После правок `server.js` и `index.html` — обязательно `./deploy.sh`. Порты и пути БД не меняются, Dockerfile/docker-compose.yml не трогаем (volume `vcode_sqlite_data` сохранит данные; миграция `todos.user_id` выполнится при старте backend в контейнере).

## Не входит в задачу (out of scope)
- Восстановление пароля по email (email не собираем)
- Смена пароля и профиля в UI
- Роли/админка, ограничения на количество пользователей, приглашения
- HTTPS/домен/reverse-proxy (остаётся как есть: http://31.76.41.104:3000)
- Привязка темы и настроек к пользователю (тема остаётся в localStorage)
- Миграция legacy-задач в конкретный реальный аккаунт через UI

---
**Открытые решения (можно изменить до реализации):**
1. Существующие боевые задачи мигрируются в legacy-пользователя `legacy` со случайным паролом (не удаляются). Альтернатива: оставить `user_id = NULL` и не показывать никому, либо удалить.
2. Сессии — таблица в SQLite + httpOnly cookie на 30 дней. Альтернатива: подписанные токены в cookie без БД (без возможности logout на сервере).
3. Регистрация открытая для всех.
